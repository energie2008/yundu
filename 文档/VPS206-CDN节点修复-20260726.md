### 2.2 根因定位

通过 `curl -v https://y3.dannelblog.na.am/vless9ad966` 测试 CDN 连接，返回 **HTTP 525**（SSL Handshake Failed）。

进一步检查证书发现两个问题：

**问题一：自签名证书**
```
openssl s_client -connect 127.0.0.1:8445 -servername y3.dannelblog.na.am
→ subject = C=CN, O=YunDu, CN=y3.dannelblog.na.am
→ issuer  = C=CN, O=YunDu, CN=y3.dannelblog.na.am  ← 自签名（issuer=subject）
```

Cloudflare 与源站建立 TLS 连接时，源站（nginx 8445）返回自签名证书。Cloudflare SSL 模式为 Full（非 Strict）时本应接受自签名证书，但证书存在第二个问题导致握手失败。

**问题二：y5 证书域名错误**
```
openssl s_client -connect 127.0.0.1:443 -servername y5.dannelblog.na.am
→ subject = C=CN, O=YunDu, CN=y3.dannelblog.na.am  ← CN 是 y3，不是 y5！
```

y5.dannelblog.na.am 的证书文件 CN 为 `y3.dannelblog.na.am`，域名不匹配。nginx 旧证书未随域名更新，导致 SNI 校验失败。

### 2.3 流量路径分析

```
客户端 → Cloudflare CDN (443/TLS)
           → CF 回源到 VPS206:443
              → nginx stream (ssl_preread, SNI 分流)
                 → SNI=y3 → 127.0.0.1:8445 (nginx http, TLS 终止)
                    → 证书校验 ← ❌ 自签名 + y5 域名错误 → 525
                    → location /vless9ad966 → proxy_pass http://127.0.0.1:8458 (xray)
```

## 三、修复方案

### 3.1 生成正确证书

为所有 CDN 域名（y3/y5/y6/y7.dannelblog.na.am）重新生成自签名证书，每个证书包含正确的 CN 和 SAN：

```bash
for domain in y3 y5 y6 y7; do
    full_domain="${domain}.dannelblog.na.am"
    openssl req -x509 -newkey rsa:2048 -nodes \
        -keyout "/etc/yundu/certs/${full_domain}/privkey.pem" \
        -out "/etc/yundu/certs/${full_domain}/fullchain.pem" \
        -days 3650 \
        -subj "/C=CN/O=YunDu/CN=${full_domain}" \
        -addext "subjectAltName=DNS:${full_domain},DNS:*.dannelblog.na.am"
    chmod 644 "/etc/yundu/certs/${full_domain}/fullchain.pem"
    chmod 600 "/etc/yundu/certs/${full_domain}/privkey.pem"
done
```

### 3.2 重启 nginx

```bash
nginx -t                    # 语法检查
systemctl restart nginx     # 完整重启（reload 不够，证书缓存未刷新）
```

**关键发现**：`nginx -s reload` 不能正确刷新 TLS 证书，必须 `systemctl restart nginx` 才能让新证书生效。

y6.dannelblog.na.am: CN=y6.dannelblog.na.am ✅

## 五、技术要点与避坑指南

### 5.1 CDN 三层分流架构

```
客户端 → CF CDN (443/TLS) → VPS206:443 → nginx stream (SNI 分流) → nginx 8445 (TLS 终止)
  → location /path → proxy_pass http://127.0.0.1:{xray_port} → xray inbound (security=none)
```

| 层级 | 组件 | 端口 | 职责 |
|------|------|------|------|
| L4 | nginx stream | 443 | SNI preread 分流，不解密 TLS |
| L7 | nginx http | 8445 | TLS 终止 + location path 路由 |
| 代理 | xray | 8454/8458/8459/8501 | WS/HTTPUpgrade inbound（无 TLS） |

### 5.2 证书管理要点

1. **自签名证书可用**：Cloudflare SSL 模式为 Full（非 Strict）时接受自签名证书
2. **CN 必须匹配域名**：每个 CDN 域名的证书 CN 必须与域名一致
3. **SAN 必须包含域名**：现代 TLS 客户端优先校验 SAN，CN 是回退
4. **nginx restart 而非 reload**：更换证书后 `systemctl restart nginx`，`reload` 不刷新证书缓存
5. **证书路径**：`/etc/yundu/certs/{domain}/fullchain.pem` + `privkey.pem`

### 5.3 P14 节点配置说明

P14 在面板上标注为 "VLESS+WS+TLS+SS2022 混合"，但数据库渲染到 xray 的实际配置为 **VLESS+HTTPUpgrade+TLS**（无 SS2022 层）。因此客户端必须使用 `network=httpupgrade` 而非 `network=ws` 才能连接成功。

**后续优化建议**：
- 数据库中 P14 节点的 `transport_type` 应改为 `httpupgrade` 以与实际配置一致
- 或修改渲染器使其按面板预设（WS）正确生成 xray inbound
- SS2022 混淆层目前未渲染到 xray inbound，需要渲染器支持

### 5.4 测速结果波动说明

CDN 节点测速可能因以下原因出现波动：
- Cloudflare CDN 边缘节点缓存旧的 525 错误响应
- xray 进程启动时的竞态条件（首次启动偶尔失败）
- CF CDN 到源站的回源延迟

**建议**：测速时每个节点重试 2-3 次，取最佳值。

## 七、未解决风险与后续建议

1. **证书自动化续期**：当前为手动生成的自签名证书（10 年有效期）。建议修复 node-agent 的 ACME DNS-01 证书管理器，使其能自动签发 Let's Encrypt 证书，避免证书过期问题。

2. **P14 节点配置不一致**：面板标注 VLESS+WS+TLS+SS2022，实际为 VLESS+HTTPUpgrade+TLS。需要修正数据库配置或渲染器逻辑。

3. **nginx reload 证书缓存问题**：`nginx -s reload` 不能正确刷新 TLS 证书，需要调查是否为 nginx bug 或配置问题。

4. **CDN 525 错误缓存**：Cloudflare 可能缓存旧的 525 错误响应。建议在更换证书后通过 Cloudflare API 清除缓存（需 CF API Token）。

5. **证书 SNI 路由**：nginx stream SNI 分流依赖 `$ssl_preread_server_name`，所有 CDN 域名都路由到 8445。如果未来需要不同域名路由到不同后端，需要修改 stream map 配置。
